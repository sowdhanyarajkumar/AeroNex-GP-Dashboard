# AeroNex GP

AeroNex GP is a simulation-first high-altitude anti-drone operations dashboard for SIH presentation use. It shows how a modeled environmental envelope can influence simulated target tracking, predictive health, adaptive control, alerts, and historical telemetry.

The current build does **not** claim real drone detection, AI accuracy, field testing, predictive-health validation, drone neutralization, physical hardware control, or real-world deployment. Every sensor value, target position, health value, alert, and control response is generated by the backend simulation service.

## Architecture

```text
React + Vite dashboard
        │ REST polling
        ▼
Express API server
        ├── Simulation engine
        ├── Threshold alert engine
        └── Hardware-provider boundary
                │
                ▼
        PostgreSQL + Drizzle ORM
```

- `artifacts/aeronex-gp` — React/Vite dashboard and responsive operator experience.
- `artifacts/api-server` — Express REST API, simulation loop, validation, and history endpoints.
- `lib/api-spec/openapi.yaml` — source of truth for API contracts.
- `lib/api-client-react` and `lib/api-zod` — generated React Query hooks and Zod schemas.
- `lib/db` — Drizzle schema and PostgreSQL client.

## Frontend

The dashboard has:

- Live system status with online, uptime, simulation-mode, and freshness indicators.
- Environment telemetry for temperature, atmospheric pressure, humidity, and vibration.
- Synthetic target tracking plane with target coordinates, confidence, error, bearing, elevation, range, and status.
- CPSO-UKF-style predictive-health presentation using simulated health readings and history.
- Adaptive-control recommendations derived from the simulated environment condition.
- Start, pause, and reset simulation controls.
- AUTO/MANUAL simulated tracking mode and a bounded pan/tilt control surface.
- Threshold-based alerts with acknowledgement state in the UI.
- Simulated environment, health, and tracking history traces.
- `/about` system brief with the simulation boundary and future hardware roadmap.

The frontend polls REST endpoints and displays a connection-lost state if the API becomes unavailable. The design is responsive for desktop, tablet, and mobile widths.

## Backend setup

The API server is an Express 5 service. It reads `PORT` from the Replit workflow, binds to `0.0.0.0`, and mounts the API under `/api`.

The simulation engine advances smoothly every two seconds. Values stay inside realistic, bounded ranges instead of jumping randomly. Environment condition changes influence tracking confidence, tracking error, health risk, operating mode, compensation, and alerts.

The engine uses simulation providers today. The provider boundary is intentionally isolated so future sensor, camera, tracking, and servo providers can be connected without changing the dashboard contract.

## Database setup

PostgreSQL is used through Drizzle ORM. The schema stores:

- `environment_readings`
- `tracking_readings`
- `health_readings`
- `alerts`
- `system_events`

The simulation persists periodic snapshots and the history endpoints read the database, falling back to the in-memory simulation history if the database is temporarily unavailable.

## API documentation

All routes below are available under `/api`.

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/healthz` | Service health check |
| GET | `/system/status` | Online, simulation mode, running state, uptime |
| GET | `/environment` | Current simulated environment telemetry |
| GET | `/tracking` | Current simulated target telemetry |
| GET | `/health` | Current simulated predictive health |
| GET | `/control` | Current adaptive-control state and recommendation |
| GET | `/alerts` | Current threshold-based alerts |
| GET | `/history/environment?limit=48` | Environment history |
| GET | `/history/health?limit=48` | Predictive-health history |
| GET | `/history/tracking?limit=48` | Tracking history |
| POST | `/simulation/start` | Start the simulation loop |
| POST | `/simulation/pause` | Pause the simulation loop |
| POST | `/simulation/reset` | Reset telemetry to its baseline |
| POST | `/control/tracking` | Set `{ "mode": "AUTO" | "MANUAL" }` |
| POST | `/control/camera` | Set bounded `{ "pan": number, "tilt": number }` |

All request inputs and responses are validated with generated Zod schemas.

## Simulation architecture

The current simulated providers are:

- `SimulationSensorProvider` behavior — temperature, pressure, humidity, and vibration curves.
- `SimulationCameraProvider` behavior — synthetic target position and camera-facing tracking values.
- `SimulationTrackingProvider` behavior — confidence, error, bearing, elevation, range, and target status.
- `SimulationServoProvider` behavior — bounded pan and tilt values that only affect simulated state.

When environment conditions become `CAUTION` or `WARNING`, the engine changes the control mode, recommendation, compensation message, health risk, and alerts. This is a modeled relationship for demonstration only.

## Future hardware roadmap

The dashboard does not directly control hardware today. Future adapters can map:

| Hardware | Intended boundary |
| --- | --- |
| Arduino Mega | Environmental and sensor integration |
| ESP32-CAM | Camera stream |
| Raspberry Pi | Future computer-vision processing |
| BMP280 | Pressure and temperature |
| DHT11 | Temperature and humidity |
| LM35 | Temperature |
| ADXL335 | Vibration and acceleration |
| HMC5883 | Orientation and heading |
| NEO-6M | GPS |
| PCA9685 | Servo control |
| Servo / pan-tilt | Future actuation boundary |

These integrations require separate provider implementations, hardware safety review, and explicit validation before they can affect any physical device.

## Development commands

This repository is a pnpm workspace:

```bash
pnpm install
pnpm --filter @workspace/db run push
pnpm --filter @workspace/api-spec run codegen
pnpm --filter @workspace/api-server run dev
pnpm --filter @workspace/aeronex-gp run dev
pnpm run typecheck
pnpm run build
```

Replit runs the API and frontend through their managed workflows. The web app is served at the root preview path and the API is routed at `/api`.

## Production / Replit deployment

1. Keep `DATABASE_URL` configured in the Replit environment.
2. Run the workspace typecheck and build commands.
3. Use the `artifacts/api-server: API Server` and `artifacts/aeronex-gp: web` workflows for development previews.
4. Publish the project from Replit. Replit provides the production URL after publishing; do not hardcode or infer it from the development domain.

The app binds to the workflow-provided `PORT` and uses the artifact routing layer, so no localhost URL is embedded in the frontend.
